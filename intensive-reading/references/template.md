## 六条硬性约束

违反这几条，构建脚本认不出角色（或直接报错），排版会退回默认样式：

1. **封面区最后两个加粗段必须是「英文主标题 + 中文标题」**，顺序不能反、后面不能
   再加别的加粗行——`postprocess.py` 靠位置认这两行给 30pt / 23pt。
2. **词条正文用段落，但辨析用表格。** 原件的词条是「`▶ ` 词条头 + 若干缩进正文行」，
   连续说明写成段落；**多维对照该用表格**——词性/含义/例句、近义语气对照、
   时态对照、单复数与谓语，这类三四列的比较用段落写反而更难读。
   界线是：表格用来**对照**，不用来装连续散文。
3. **封面的三行副信息之间要留空行**，否则 Markdown 会把它们并成一段。
4. **`译:` 行必须写在引用块 `> ` 里**，`En:` 行不写引用块——这一对是靠这个区别识别的。
5. **新增 emoji 前先查 `scripts/print_variant.py` 的 `GLYPH_MAP`。** 没映射的 emoji
   会被字形校验拦下（构建失败），不会静默变成空白。
6. **反引号 `` ` `` 内不要嵌套 `**加粗**`。** 形如 `` `一段文字 **加粗** 文字` `` 的写法，
   pandoc 不会解析代码 span 内部的 `**`，导出后会看到字面星号，而且不报错、不失败——
   是最容易被写手和构建脚本双重漏过的一类坑（历史上在同一批稿子里反复出现过十几次）。
   加粗和行内代码要混用时改成 `*一段文字 **加粗** 文字*`（外层斜体+内层加粗，不用反引号），
   或者干脆分开写。**源码级 grep 反引号不可靠**（会在多段不相关的反引号之间产生误判），
   真正可靠的复查方法是构建后对成品 PDF 跑
   `pdftotext file.pdf - | grep -oP '\*\*[^ ]'`——命中说明有真实残留，逐行用正则修
   （不要整篇贪婪替换，容易连带匹配到不相关内容），修完重新构建再复查到 0 命中。
